Video's saved camera changes from `{ yaw: 0.8, pitch: 0.2, roll: 0.1, distance: 4.2 }` to
`{ yaw: 0.3292, pitch: 0.0178, roll: 0.061, distance: 1.25 }`. Both actual JSON downloads contain
the changed pose; pan remains `[0.1, -0.1, 0.05]`. This is a persistence failure, not merely a
normalization comparison.

An isolated component probe loads historical `src/video3d/flight.js` implementations with the same
synthetic camera path and current orbit camera. Parent `82bbd809f84389a37161ac747ed64683b6aa1f2b`
preserves the idle pose. Commit `54035cffbd3191263688438e35afa8f585252bda` adds the initial
`place(...)` call and changes it; the current implementation changes it too. This establishes the
introducing driver change, alongside the current browser download evidence. Historical pages were
not run in browsers.

Photo's first saved-view implementation, `e2ab4b352a7d529b5362c440ddf9a0af2cae7577`, calls
`fromScene` during `sharpPhoto` / `sharpClip`. It reads `window.__splashery.player`. The embed
exposes that player only after `await viewer.start()`. The historical component probe selects Splats
when the player is bound before the build and keeps Sharp picture when binding occurs after the
build. Current real-browser checks reproduce the saved-view mismatch in both photo toys. This
identifies a startup-order omission in the saved-view feature; the probe uses synthetic binding
timing, not a historical-page browser bisect.

Suggested follow-up: **Engine: Restore saved Studio camera and views during startup.** Pass restored
scene settings into the first Studio build, apply the saved photo view before building the relief,
and prevent the video's automatic opening pose from replacing an explicitly restored camera. Keep
the native opening pose for a newly chosen video sample. Reuse these actual download/reload and
embed assertions, and keep v2/v3 inputs and the 120-second / 30 MB thresholds. Protected PR files
and engine code prevent including that fix here. No separate fix PR, merge, or deployment was
started.

All 93 supported scene cases produced first and reloaded JSON downloads. The v1 scene was refused on
all three visitor routes and left the existing file-import scene unchanged. World schema v1 is
separate; its byte provenance and normalization checks pass, while its render/spawn/prop/reload
checks remain unrun after construction times out.
