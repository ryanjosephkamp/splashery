# Real places to walk through

October 17, 2026. Research and recommendations: Codex (GPT-6).

Start with **Small Garden**, then a room we capture ourselves. Use COLMAP and native Brush on the
Mac, and deliver larger places through PlayCanvas's streamed SOG. The catalog below contains **28
captured places: 16 downloadable splats, eight heritage surveys, and four mesh alternatives**. This
is a source-based ranking, not a completed visual, collision, or phone-performance audit.

## The ten best, in order, and how to bring them in

These are proposed routes, not claims that hidden rooms or unphotographed surfaces exist. For each S
entry, use its licensed Download action, preserve its credit, and inspect the obtained format:
export the highest-detail level to PLY if the download is streamed, then clean and build phone
tiers. Self-host approved derivatives; an external viewer embed would add third-party code and
requests. For M entries, obtain the textured mesh, retain a simplified collision mesh, and try
`node tools/model-to-splats.mjs model.glb --splats 500000 --no-light` as an initial tier.
[Model to splats](../../tools/model-to-splats.mjs) samples surfaces rather than training from
photos; it normalizes to a unit sphere, so restore measured scale and the identical transform on
collisions. For H entries, verify RGB, scan registration, and actual package contents first: LiDAR
points alone are not trained, view-dependent splats, and a photoreal result is not guaranteed.

## Capture your own room or garden, then train on the Mac

1. **Capture a bounded route.** Proposed starting targets: 200–400 sharp stills for one room, or
   300–600 for a small garden section. Budget 15–30 minutes for shooting/review as a planning
   allowance, not a benchmark. PlayCanvas recommends 200–500+ for environments, 70–80% overlap,
   several heights, and consistent lighting. Use one phone lens/zoom, lock exposure/focus where
   possible, move between views, and cover the floor, corners, doorways, and obstacles from both
   sides. Avoid mirrors, changing light, people, and wind-blown plants
   ([capture guide](https://developer.playcanvas.com/user-manual/gaussian-splatting/creating/taking-photos/)).
2. **Transfer locally.** Copy original JPG/PNG images to `scene/images`; review blur before solving.
   A slow overlapping video can supply frames, but stills are the simpler first attempt. COLMAP
   needs parallax, overlap, and multiple views of each feature; rotating in place cannot establish
   the route's geometry ([COLMAP tutorial](https://colmap.github.io/tutorial.html)).
3. **Solve camera positions.** Install COLMAP with Homebrew and use its CPU extraction/matching on
   the Mac. The following follows the current CLI; check installed help because older versions use
   `SiftExtraction`/`SiftMatching` flag names
   ([installation](https://colmap.github.io/install.html),
   [CLI](https://colmap.github.io/cli.html)):

```sh
brew install colmap
mkdir -p scene/images scene/sparse
colmap feature_extractor --database_path scene/database.db --image_path scene/images --ImageReader.single_camera 1 --FeatureExtraction.use_gpu 0
colmap exhaustive_matcher --database_path scene/database.db --FeatureMatching.use_gpu 0
colmap mapper --database_path scene/database.db --image_path scene/images --output_path scene/sparse
```

4. **Inspect, then train.** Confirm one connected camera solution covers the whole route. Download
   native Apple-silicon Brush, open the COLMAP dataset, train with the live preview, compare input
   views, and export PLY. If the chosen build needs undistorted images, use COLMAP's
   `image_undistorter`; dense stereo is unnecessary for this sparse-camera training workflow. Brush
   supports macOS and COLMAP input and is Apache-2.0
   ([README](https://raw.githubusercontent.com/ArthurBrussee/brush/main/README.md),
   [releases](https://api.github.com/repos/ArthurBrussee/brush/releases/latest),
   [license](https://raw.githubusercontent.com/ArthurBrussee/brush/main/LICENSE)).
5. **Clean and deliver.** In SuperSplat, remove floaters, level the floor, set a measured scale,
   restrict the walk boundary, and export SOG or generate streamed tiers below. Keep the original
   photos, camera solve, PLY, versions/settings, held-out views, and separate timings for solving,
   training, cleanup, and compression. Inspect held-out views along the route for blur, holes, and
   reflective artifacts
   ([editing workflow](https://developer.playcanvas.com/user-manual/supersplat/)).

**Time and quality evidence:** no sufficiently specified Brush room-training benchmark was verified,
and CPU camera-solving time on the owner's Mac is unknown. The alternative Apache-2.0 Metal trainer
[msplat](https://raw.githubusercontent.com/rayanht/msplat/main/README.md) requires Apple silicon and
macOS 14+: install in a virtual environment with `pip install 'msplat[cli]'`, then try
`msplat-train scene -n 7000 --num-downscales 0 --eval`. Its author reports M4 Max prepared-dataset
training: room, 7K steps, **74 seconds, PSNR 30.12, SSIM 0.897**; garden, 7K, **77 seconds,
25.68/0.783**; garden, 30K, **700 seconds, 27.14/0.853, 3.51M splats**. These exclude capture and
camera solving, are not reproduced here, and do not predict an unspecified Mac's total time. More
training cannot recover unobserved surfaces. Keep trainers as offline build tools; the
[original Graphdeco trainer](https://raw.githubusercontent.com/graphdeco-inria/gaussian-splatting/main/README.md)
requires CUDA and is not the native Mac route.

## Showing a big scene on a phone

**Recommendation:** spatially chunked, multilevel **Streamed SOG**, a coarse scene first, nearby
refinement under a global budget, and eviction of distant data. Use the existing PlayCanvas engine;
its
[2.22.3 parser](https://raw.githubusercontent.com/playcanvas/engine/v2.22.3/src/framework/parsers/gsplat-octree.js)
recognizes `lod-meta.json`. Engine capability does not establish that Splashery's file loader
already integrates a streamed directory. Keep a small single-SOG fallback until that integration
passes.

SOG typically compresses equivalent PLY by 15–20× through lossy quantization. Streamed SOG uses
`lod-meta.json` plus **unbundled** per-chunk `meta.json` and WebP files, not one giant archive or
bundled `.sog` chunks. Hosting is ordinary static files; preserve relative paths. Choose one detail
level per spatial region, cull outside the view, and bound both rendered and resident counts
([SOG specification](https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/sog/),
[streamed specification](https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/streamed-sog/)).

The repository pins SplatTransform 3.6.1; its local `--help` confirms these options. The following
official recipe was checked against help, not run on a captured scene. Crop first; compare adaptive
decimation for mixed-scale foliage, and measure output bytes rather than predicting a fixed ratio
([generation guide](https://developer.playcanvas.com/user-manual/splat-transform/streamed-sog/)):

```sh
npx splat-transform source.ply -d 50% lod1.ply
npx splat-transform source.ply -d 25% lod2.ply
npx splat-transform source.ply -d 10% lod3.ply
npx splat-transform source.ply -l 0 lod1.ply -l 1 lod2.ply -l 2 lod3.ply -l 3 output/lod-meta.json --filter-nan
```

Actual phone evidence: PlayCanvas reports an **iPhone 13 Pro Max at 642×1126** drawing 1M/2M/3M/4M
splats at **38.1/35.5/25.5/20.4 fps with WebGL 2**, and **77.6/73.2/52.7/42.4 fps with WebGPU**.
Those are vendor measurements, not Splashery walkthroughs, Android results, or thermal tests
([June 3 benchmark](https://blog.playcanvas.com/new-in-supersplat-webgpu-and-streaming-bring-huge-performance-wins/)).
SuperSplat's documented mobile budgets are 1M in Performance Mode and 2M otherwise; counts alone do
not guarantee fps
([streaming guidance](https://developer.playcanvas.com/user-manual/supersplat/streaming/)). File
scale in this repository: [maple-tree.sog](../../assets/toys/maple-tree/maple-tree.sog) contains 1M
splats in 14,899,748 bytes; its lite tier contains 300K in 3,883,165 bytes (file and embedded
`meta.json` inspection). These are delivery examples, not memory or walking benchmarks.

Alternatives: [SPZ](https://raw.githubusercontent.com/nianticlabs/spz/main/README.md) reports about
10× PLY compression but does not itself provide scene LOD selection;
[Spark](https://sparkjs.dev/docs/lod-getting-started/) offers paged `.rad`/`.radc` trees but adds a
different runtime. [Octree-GS](https://arxiv.org/html/2403.17898v2) learns a multiresolution scene;
its A100 80 GB experiments do not establish phone speed or a native Mac/PlayCanvas import path.

## Floors, walls, comfort, and the release gate

Separate visible splats from collision geometry. Prefer a simplified captured mesh where available;
otherwise calibrate up/scale, fit a robust floor plane, remove floaters, and author wall/obstacle
proxies. PlayCanvas's
[collision tool](https://developer.playcanvas.com/user-manual/splat-transform/collision/) can
voxelize splats, fill enclosed-room exteriors or outdoor ground, carve a capsule-reachable region,
and emit `.voxel.json`/`.voxel.bin` or `.collision.glb`. Holes and glass require manual review;
never infer a safe floor merely from opacity. Cache collision data separately from visible LODs.

[SuperSplat Walk Mode](https://blog.playcanvas.com/new-in-supersplat-walk-mode-streamed-lod-and-easy-upload/)
demonstrates tap-to-walk and voxel collision. For Splashery, use a capsule, gravity, wall sliding,
explicit capture boundaries, and a safe reset; propose a fixed eye height, gentle speed, no head
bob/roll, and optional touch sticks. Honor reduced motion with instant viewpoint transitions and
optional turning vignette; test comfort rather than promising no sickness
([W3C motion guidance](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)).

**Proposed gate; no phone run was performed for this report.** Follow
[task 115](../codex/115-walk-inside.md) and [the phone/transfer rules](../../builders/RULES.md),
with these measurable additions:

- Test real iPhone 13-class Safari and a named midrange Android/Chrome device; log OS, browser,
  renderer, drawing-buffer size, scene hash, and drawn/resident counts. Start at 500K drawn splats,
  allow 1M only while timing holds, cap the buffer near 720K pixels, and disable MSAA.
- After five minutes of active warm-up, run a fixed three-minute route with turns and dense foliage:
  mean ≥30 fps, p95 frame interval ≤34 ms, p99 ≤67 ms, and no stall >250 ms. Log frame intervals,
  not just a screenshot of an fps counter; test both WebGPU and the WebGL 2 fallback.
- Cold cache at 10 Mbps/80 ms RTT: usable coarse view and controls within eight seconds, ≤6 MiB
  before interaction, default first load ≤15 MB, and no file >20 MB. Keep the existing embed
  transfer ≤30 MB test green; reserve a ≤40 MB route for an explicit higher-quality opt-in.
- Across three route loops: no context loss, tab reload, or growing scene allocation trend. Report
  decoded buffers/textures separately from network bytes; browser-wide memory may be unavailable.
- Run ten deterministic walks per test place: no floor fall-through or wall penetration, intended
  doors passable, endpoint within 10 cm, and reset always reachable. Review the route at phone size
  for holes, reconstructed surfaces, and LOD popping. If it fails, shrink the route/detail, or use
  linked viewpoints until it passes. These are acceptance targets, not measured capacity claims.
